# 第 7 章｜Agent 框架怎样分层（中文版）

来源：[Hello-Agents 第 7 章](https://github.com/datawhalechina/hello-agents/tree/main/docs/chapter7)。我关注的是哪些逻辑可以共用，以及一次任务怎样经过各层。

[English version](en/07-agent-framework.md)

## 从一个循环变成可复用系统

第 4 章的示例可以在一个程序里完成“提问—选工具—执行—回答”。项目扩展后，换模型、换 Agent 范式、加工具都会碰到相同的消息和错误处理。把这些共用职责拆出来，不同 Agent 才能复用同一套底层能力。

```text
用户 / 应用
    ↓
Agent（任务入口、执行循环、结束条件）
    ├── Message / History（这一轮已发生什么）
    ├── LLM 接口（向模型发送信息，取得回复）
    ├── Tool Registry / Executor（发现并执行允许使用的工具）
    └── Config（模型、预算、运行参数）
```

框架的文件划分可以不同，但这些职责都要有人承担。统一接口让不同范式共用模型调用、消息和工具接入。

## 一轮请求在各层之间怎么走

1. 应用把用户任务交给某个 Agent。Agent 根据任务、系统要求和历史消息准备模型输入。
2. LLM 接口处理模型连接与请求，返回模型的回答或工具调用意图。
3. 如果需要工具，Agent 通过注册表确认工具是否可用，把参数交给执行层；执行结果以消息形式放回历史。
4. Agent 再次调用模型，让它看到工具结果，决定继续行动还是给出答案。
5. 达到结束条件后，返回结果，并保留下一轮确实需要的状态。

这里要分清：模型提出动作，程序负责执行。Tool Registry 管理可调用工具；执行层真正调用工具，并处理失败或超时。

## 各层的职责

- **LLM 统一接口**：Agent 不必关心每个模型提供商的连接细节。切换模型时尽量不动上层流程；但不同模型的工具调用和输出能力仍可能不同，统一接口不能抹平所有差异。
- **Message**：把用户、系统、助手和工具的内容表示成统一消息。这样历史可以被保存、筛选和转换为模型接口所需的格式。若消息形态混乱，后面的上下文工程也无从谈起。
- **Config**：把模型选择、温度、历史长度等可调整参数集中管理。改策略时不用在每一种 Agent 里寻找硬编码值。
- **Agent 基类与具体范式**：对外保留相似的运行入口，内部可以分别实现普通对话、ReAct、规划执行和反思。调用者只需知道“交任务、取结果”，不必理解每种范式的全部内部步骤。
- **工具系统**：统一名称、说明、输入和输出。注册表回答“有什么工具”；执行层回答“调用后发生了什么”。记忆、检索或协议能力也可以从统一的工具入口接入。

“万物皆为工具”对我最有用的是统一调用入口：Agent 用相同方式发现和调用能力。内部实现仍各不相同；记忆维护状态，RAG 管文档与检索，协议工具还要处理远端连接。

## 设计取舍与排错思路

分层会增加文件和接口，简单的一次性脚本未必需要完整框架。只有当多个 Agent 共享模型、消息或工具逻辑时，抽象才真正减少重复。抽象也不应把关键流程藏得看不见：遇到异常时，仍要能知道是模型输出、消息转换、工具选择还是工具执行出了问题。

如果 Agent 选错工具，我会按链路定位：模型看到的工具说明是否明确？返回的工具名和参数是否可解析？注册表有没有这个工具？工具的实际返回是否被正确放回消息？这样排查比笼统地修改提示词更有针对性。

## 我记住的运行链路

任务从 Agent 入口进入；模型返回回答或工具调用意图；程序检查并执行动作；工具结果作为消息回到下一轮。分层的价值是让不同 Agent 复用底层能力，也让换模型、加工具和排查故障时的修改范围更清楚。
