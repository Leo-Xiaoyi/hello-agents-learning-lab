# 第 8 章｜记忆与 RAG（中文版）

来源：[Hello-Agents 第 8 章](https://github.com/datawhalechina/hello-agents/tree/main/docs/chapter8)。我把记忆和 RAG 分开记：前者处理交互中留下的信息，后者处理外部文档。

[English version](en/08-memory-and-rag.md)

## 两类信息从哪里来

一次模型调用只处理本次送进去的内容。当前会话的消息可以暂时放在程序的历史列表里，但程序重启或会话切换后，这个列表并不能自动告诉新会话此前发生了什么。另外，模型也不会自动得到用户的文档或最新的外部资料。

两条信息路径：

```text
过去的交互、偏好、事件 → Memory：记下、维护、按需找回
外部文档、知识库       → RAG：预处理、建立索引、按问题检索
                                     ↓
                        相关结果进入本轮上下文
```

它们都能“找资料”，但资料的来源和维护目标不同。对话中形成的事实属于记忆；某份手册里的段落属于外部知识库。把两者分开，才能知道答案依据来自用户过去说过的话，还是来自某份可追溯的文档。

## 记忆系统的一条主线

```text
新交互 → 判断是否值得记 → 按类型存储
新问题 → 按问题检索相关记忆 → 送入当前上下文
长期运行 → 过期清理、整合或修正
```

四类记忆的保存和找回方式不同：

| 类型 | 主要保存什么 | 设计关注点 |
| --- | --- | --- |
| 工作记忆 | 当前任务或会话的临时信息 | 快速使用、容量与过期时间 |
| 情景记忆 | 发生过的具体事件或交互 | 事件、时间和上下文能否找回 |
| 语义记忆 | 比较稳定的概念、规则与偏好 | 抽象整理、长期有效性与冲突处理 |
| 感知记忆 | 图像、音频等多模态信息 | 模态表示与跨模态检索 |

### 我当时问：Conversation History 和 MemoryTool 会不会重复？

它们确实可能保存相近的近期信息，但职责不同。`conversation_history` 是当前对话的消息记录，Agent 可以直接拿它接着聊；`MemoryTool` 负责按需写入和找回记忆，还要处理不同类型记忆的保存期限。工作记忆可能与对话历史重叠，情景记忆则是从交互中保留下来的事件，并非把所有聊天记录永久存一份。

一个可靠的记忆系统需要的不只是“写入”。旧信息可能已失效，用户偏好可能改变，重复事件可能需要合并。如果只会不断积累，后续检索就会把过时内容重新送给模型。

## RAG 是两段流水线

准备知识库时：

```text
文档 → 提取并统一文本格式 → 按合适边界分块
     → 为块建立可检索的表示和来源信息 → 存储
```

回答问题时：

```text
问题 → 检索候选块 → 选择相关证据
     → 连同问题交给模型 → 基于证据生成答案
```

教程里的处理流程是先把文档转成 Markdown，再利用标题等结构分块。我把分块和向量化分开记：前者组织文本，后者提供一种检索表示。块太大，可能带进无关信息；块太小，又可能切断完整意思。标题和来源也要跟着块保存。

检索不一定只靠一种方法。关键词匹配适合明确术语；向量检索能利用语义相似性，但也可能漏掉精确名称或召回不相关内容。教程还介绍多查询扩展（MQE）和假设文档嵌入（HyDE）：前者用不同表述扩大候选范围；后者先形成一个“可能的答案式文本”来帮助检索。**HyDE 生成的文本是找资料用的查询线索，不是最终答案或事实证据。** 扩大召回之后，仍需要筛选真实文档。

## 它们怎样在一轮问答里配合

收到问题后，系统可以分别查记忆和知识库。两路各自返回带来源的候选信息，再由上下文构建环节选出本轮要用的内容。回答生成后，系统还要判断有没有值得写入记忆的新事实。

如果答案不准确，我会先区分故障位置：资料根本没入库？文档切坏了？检索没找到？找到了却没有被选进上下文？还是模型没正确使用证据？只有定位到阶段，改进才不会变成一味增加更多资料。
