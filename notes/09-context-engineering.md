# 第 9 章｜上下文工程

来源：[Hello-Agents 第 9 章](https://github.com/datawhalechina/hello-agents/tree/main/docs/chapter9)。我把上下文工程理解为：每次调用模型之前，先决定这轮给它看什么。

## 一次模型调用需要准备哪些信息

提示词是模型输入的一部分。一次调用还可能包含系统要求、当前问题、历史消息、相关记忆、检索出的文档、笔记和刚刚得到的工具结果。上下文工程要决定这一次放进哪些信息，以及怎样组织。

信息越多并不一定越好：会消耗 token，可能让重要内容被淹没，也可能把过时或相互矛盾的材料一起送进去。所以它既要找得到相关信息，又要舍得排除无关信息。

```text
用户问题
   ↓
从历史、记忆、RAG、笔记、工具结果等来源找候选信息
   ↓
按任务相关性与预算选择 → 分区组织 → 最终长度检查
   ↓
构建好的上下文 + 当前问题 → 模型 → 回答
   ↓
必要时把本轮的重要新信息写回记忆或笔记
```

构建好的上下文是本轮准备送给模型的输入。回答之后是否写入长期记录，还要另行判断。

## 所有 Agent 能不能共用一个 ContextBuilder？

可以。每个 Agent 都自己拼上下文的话，增加记忆源或调整预算就要改多处。`ContextBuilder` 提供统一入口，各 Agent 需要时调用它；筛选和组织策略留在一处维护。

另一个问题是：为什么每条候选信息都要包装成 `ContextPacket`，连 token 数量也记下来？因为后面要比较、排序，还要在预算内筛选。没有统一结构和长度信息，这一步很难做。`ContextConfig` 集中保存预算、阈值和权重，调整策略时不用到处找参数。

## Gather → Select → Structure → Compress

**Gather：先找候选，不急着全部发送。** 根据当前问题，分别获取近期对话、相关记忆、RAG 文档、已有笔记或专用工具结果。这里要保留来源，不能把“用户以前说过的话”和“外部资料”混成一整段。单一路检索失败时，其他可用信息仍可继续提供，但失败本身不能被当成“没有相关资料”。

**Select：选本轮真正需要的。** 系统要求应先保留；其他信息再看与问题的相关性、时间、重要性和 token 成本。教程的示例主要用相关性与新近性评分，再按预算选入。近不等于重要：一条较早但决定当前任务的约束，可能比刚刚发生的闲聊更值得保留。如果 Builder 经常选入不相关内容，该改什么？先查候选检索和相关性评分，而不是直接把预算加大。

**Structure：让每类信息待在自己的位置。** 教程把输入组织为角色与规则、任务、状态、证据、上下文和输出要求等区块。外部文档检索结果放在 Evidence；历史对话和记忆放在 Context。分区让模型和人都更容易看出“这是要求、这是事实来源、这是过去发生的事”，也便于排查哪一块污染了答案。

**Compress：最后兜底检查长度。** 每条候选信息单独选入时没有超限，不代表拼上区块标题、任务和输出要求后仍在预算内。教程因此在形成最终文本后再检查一次；超限时压缩或截短。压缩要留住目标、关键约束和依据，不能只按字数机械删除。

## 按需找，比一次塞满更有方向

“渐进式披露”让我想到一个取舍：先保留轻量的索引、路径或目录，需要时再用工具打开具体内容。上下文少了，但查找可能变慢，也可能走错路径。我的理解是先放必要的规则和项目概览，再让 Agent 按需深入。

`NoteTool` 适合记长期任务的阶段结论、下一步和阻塞项。索引帮助找到笔记，具体内容仍在 Markdown 笔记里；教程示例中的简单搜索也不能当作“理解全部语义”的检索器。`TerminalTool` 适合即时查看文件或日志，但需要限制可执行操作和访问范围。它们与 `MemoryTool`、`RAGTool` 并不是互相替代：来源不同，读取时机也不同。

长任务跨很多轮时，我关心的是：上下文快满了，阶段结果怎么留下来？一种办法是压缩已有对话，保留决策、进度和阻塞项；另一种是定期写结构化笔记，下一轮按需检索。任务能拆开时，也可以由子 Agent 分别处理，再汇总结果。这些方法处理的是跨多轮的连续性；GSSC 末尾的压缩处理的是单次输入拼好后超长的问题。

## 我记住的处理顺序

每轮调用前，先根据当前问题从各来源找候选信息，再按相关性和 token 预算筛选。系统规则、任务、外部证据和历史上下文分开放，拼好后检查总长度。模型回答以后，再决定是否记录新的长期信息。
