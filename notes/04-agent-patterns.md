# 第 4 章｜ReAct、Plan-and-Solve 与 Reflection

来源：[Hello-Agents 第 4 章](https://github.com/datawhalechina/hello-agents/tree/main/docs/chapter4)。我把三种范式理解成把循环放在不同位置。

## 三种方式的区别

复杂任务常常需要多次模型调用。ReAct 在行动过程中不断根据结果调整；Plan-and-Solve 先定步骤再执行；Reflection 在初稿出来后检查和修改。一个任务也可能同时用到几种方式。

## ReAct：根据新结果决定下一步

```text
接收问题 → 判断需要什么信息或动作 → 调用工具
        → 读取工具结果 → 更新当前判断 → 再行动或回答
```

模型提出动作，程序解析和执行，再把结果送回下一轮。比如搜索没找到足够可靠的信息，下一轮可以改搜索词。它适合路径事先不确定、必须边查边决定的任务。

我特别记下两处边界：工具结果只是一条新观察，还要判断它能否回答原问题；模型提出调用意图，程序才去识别工具名、检查参数并执行。如果工具不存在或执行失败，也由程序处理。

ReAct 的代价是多轮模型调用，可能慢，也可能反复兜圈。明确可用工具、记录每一步、设置最大步数和结束条件，才能让动态决策保持可控。

## Plan-and-Solve：先有全局路径，再逐步执行

```text
原始任务 → 形成步骤计划 → 按步骤执行
                   ↑            ↓
                   └── 必要时检查或调整计划
```

这种方法把整体规划和当前步骤分开。执行时要保留原任务、计划和前面步骤的结果，避免后面的步骤丢掉目标或重复劳动。它适合可以拆解、步骤之间有依赖的任务。

计划的价值是让后续执行有方向；风险是第一版计划本身可能有错，或中途出现新信息。因而“先规划”不等于“计划永远不能改”。需要有检查点：当步骤无法执行、关键前提不成立或结果与目标偏离时，回到规划层调整，而不是机械走完。

## Reflection：有了初稿，再给它一次有依据的复查

```text
生成初稿 → 按任务要求检查问题 → 给出具体反馈 → 修改初稿
                                      ↘ 满足要求或达到上限时结束
```

Reflection 主要检查已有结果是否达到要求。检查时可以看有没有遗漏约束、依据是否足够、逻辑是否连贯、格式是否符合要求。反馈要指出具体问题，下一轮修改才有方向。

它不是让模型无限次说“再优化一下”。如果没有明确检查标准或外部验证，同一个模型可能反复改写措辞，却没有提高正确性。因此要设定检查目标、迭代上限，并在有可验证依据时优先使用依据。

## 放在一起比较

| 任务中的主要难点 | 优先考虑 | 需要留意 |
| --- | --- | --- |
| 新信息不断出现，下一步难预定 | ReAct | 工具错误、循环和成本 |
| 任务可拆解，但要保持整体目标 | Plan-and-Solve | 错误计划和中途变化 |
| 初稿质量需要检查与修正 | Reflection | 反馈是否具体、是否真的改善 |

三种方式可以组合：先规划阶段，某一步用 ReAct 查资料，得到答案后再做 Reflection。我会先看不确定性在哪：是下一步不知道怎么走，还是已有结果需要复查。循环放在哪里，就在哪里设停止条件。
