# 第 10 章｜MCP、A2A 与 ANP

来源：[Hello-Agents 第 10 章](https://github.com/datawhalechina/hello-agents/tree/main/docs/chapter10)。我按连接对象区分 MCP、A2A 和 ANP。

## 不同系统怎样接上

单个 Agent 可以把本地函数注册为工具。但接入更多外部服务时，如果每个系统都要单独约定工具说明、输入格式、连接和错误处理，集成成本会不断增加。与另一个独立 Agent 协作时，还要说明对方能做什么、任务如何提交、结果如何返回。通信协议的意义，是给不同系统一个可复用的交互约定。

三种连接关系：

```text
Agent 所在应用 ── MCP ── 工具 / 资源 / 提示
Agent A        ── A2A ── Agent B 的能力与任务
开放网络中的 Agent ── ANP ── 身份、描述、发现与连接
```

它们处理不同的连接问题。应用仍要管理权限、状态和业务逻辑。

## MCP：把外部能力接到 Agent 所在应用

MCP 采用 Host、Client、Server 的结构。Host 是运行 Agent 的应用；它为所连接的服务器管理客户端连接；Server 对外提供能力。服务器不只可以提供可执行的 **Tools**，还可以提供供应用读取的 **Resources** 和可复用的 **Prompts**。

```text
应用连接 Server → 发现可用能力 → 选择并调用/读取
              → 得到结果 → 应用决定如何交给模型
```

我把协议和任务控制分开：MCP 规定能力与数据怎样交换，Agent 仍要决定是否调用、怎样使用和怎样控制权限。Server 返回内容后，应用还要决定哪些信息进入本轮模型输入。

## A2A：把任务交给另一个 Agent

另一个 Agent 可能有自己的工具、状态和较长的执行过程。A2A 处理能力说明、任务提交、消息交换和结果返回。任务交互大致是：

```text
发现对方能力 → 发起任务与必要上下文
            → 跟踪任务状态 / 交换消息
            → 接收结果或产物
```

这适合将有独立职责的 Agent 作为服务协作。关键设计问题包括：发给对方多少上下文、怎样知道任务是否完成、失败时谁负责重试，以及最终结果由谁验证。不是任务一复杂就必须“多 Agent”；如果一个明确的流程加几个工具就能完成，引入多个 Agent 只会增加通信和协调成本。

## ANP：把发现和互联的问题扩展到开放网络

教程把 ANP 放在更开放的网络场景：Agent 怎样公开自己是谁、能做什么、怎样被找到并与别的系统建立可信连接。它关注身份、能力描述、服务发现和跨域交互等基础问题。它与 A2A 都涉及 Agent 之间的联系，但观察角度不同：A2A 更直接地描述任务协作；ANP 更强调开放网络中的**身份与发现基础**。

因此我不会把三者机械理解为“小系统用 MCP、中系统用 A2A、大系统用 ANP”。MCP 面向应用与外部能力；A2A 面向 Agent 间的任务交互；ANP 讨论开放网络中的互联条件。需要哪个，取决于实际要跨越的系统边界。

## 协议在整个系统里的位置

协议处理系统之间怎样接通。接通以后，Agent 循环仍决定下一步；工具系统管理能力；记忆与 RAG 提供信息；上下文工程筛选本轮输入。结果是否可信，也要由应用判断。
